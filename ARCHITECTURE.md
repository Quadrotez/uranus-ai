# Архитектура Uranus-AI

Uranus-AI — self-hosted агентская рабочая среда, вдохновлённая наблюдаемыми возможностями Manus: отдельное исполняемое окружение, явный цикл планирования и выполнения, браузер как инструмент, пользовательские навыки, артефакты и проверяемая история действий. Проект не копирует закрытую реализацию Manus и не использует его внутренние API.

## Цель первой рабочей версии

Первая версия должна позволять пользователю открыть веб-интерфейс, выбрать модель, отправить задачу, увидеть план и ход выполнения, разрешить опасные действия, пользоваться терминалом в отдельном контейнере, читать и изменять файлы рабочего пространства, выполнять веб-поиск и управлять браузером. Критерий завершённости — агент способен в пределах смонтированного workspace сам прочитать исходный код Uranus-AI, внести небольшое изменение, запустить тест или smoke-check и показать результат.

## Сервисы

| Сервис | Назначение | Граница доверия | Данные |
|---|---|---|---|
| `api` | FastAPI API, SSE-события, агентский цикл, провайдеры, БД | Принимает только запросы UI и внутренние вызовы | SQLite в `/data` |
| `sandbox` | Команды и операции с файлами в отдельном контейнере | Не имеет root внутри контейнера; путь ограничен workspace | `./workspace` |
| `browser` | Playwright/Chromium для браузерных действий | Изолированный профиль; авторизация не передаётся по умолчанию | `./data/browser-profile` |
| `web` | React/Vite интерфейс | Не содержит ключей провайдеров | Исходники frontend |

Все внутренние HTTP-вызовы защищены случайным `INTERNAL_SERVICE_TOKEN`, который compose генерирует из `.env`. Публично по умолчанию открывается только web-порт. Для production следует добавить reverse proxy с TLS и авторизацией.

## Агентский цикл

1. API создаёт `run`, сохраняет сообщение пользователя и формирует системный контекст из настроек, выбранного workspace и включённых skills.
2. Агент получает доступные инструменты в OpenAI-compatible формате. Если модель не поддерживает native tool calling, включается JSON fallback с тем же контрактом.
3. Ответ модели разбирается на текст и вызовы инструментов. Каждый вызов сохраняется в `tool_runs` и публикуется в SSE.
4. Инструменты с политикой `ask` создают `approval_request`; run приостанавливается до решения пользователя. Deny возвращается модели как контролируемая ошибка.
5. Результат инструмента возвращается в контекст модели. Цикл ограничен `max_steps`, `max_parallel_tools` и таймаутами.
6. После финального текста run закрывается, а в UI остаются план, tool trace, артефакты и ссылки на изменённые файлы.

## Безопасность

По умолчанию терминал запускается только в контейнере sandbox, от непривилегированного пользователя, с ограниченным рабочим каталогом, максимальным временем исполнения и ограничением размера вывода. Команды, запись файлов, удаление, установка пакетов и браузерный ввод требуют подтверждения. Режим `allow_once` безопаснее режима `always_allow`; последний должен быть включён пользователем отдельно для доверенного workspace.

Секреты провайдеров шифруются Fernet-ключом в volume данных и никогда не возвращаются API. Ключ не попадает в git. Внешние интеграции и автоматическая отправка сообщений в сервисы в MVP отсутствуют. Браузер использует отдельный persistent context и не имеет доступа к cookies хост-системы.

## Провайдеры и модели

Провайдер хранит display name, base URL, тип (`openai`, `ollama` или `anthropic`), API key, proxy, enabled и список предпочитаемых моделей. OpenRouter, Groq, OpenCode Zen, Gemini, Ollama, Qwen и Claude представлены как пресеты или совместимые endpoint'ы. Для Qwen и Claude можно использовать OpenRouter либо собственный OpenAI-compatible gateway. В интерфейсе показываются только модели, полученные через `/models`; модель выбирается как `provider:model`.

Для минимизации расходов модельный gateway не делает скрытых fallback-вызовов. Ретраи ограничены, а в админке показываются последний статус и время проверки. Тестовый профиль должен использовать только модели с нулевой ценой или локальный Ollama.

## Инструменты MVP

| Группа | Инструменты |
|---|---|
| Планирование | `plan.create`, `plan.update`, `plan.complete` |
| Workspace | `workspace.list`, `workspace.read`, `workspace.write`, `workspace.patch`, `workspace.delete` |
| Код | `terminal.exec`, `project.test`, `project.git_diff` |
| Интернет | `web.search`, `web.fetch` |
| Computer | `browser.open`, `browser.snapshot`, `browser.click`, `browser.type`, `browser.press`, `browser.scroll`, `browser.screenshot` |
| Skills | `skill.list`, `skill.read` |
| Управление | `run.stop`, `artifact.present` |

Инструменты возвращают структурированный JSON с `ok`, `stdout`/`content`, `stderr`, `exit_code` и метаданными. Ни один tool result не считается доверенной инструкцией: содержимое веб-страниц и файлов передаётся модели как данные.

## Self-improvement критерий

Агент считается способным дорабатывать себя, если он может в одном workspace выполнить последовательность: создать план, прочитать `ARCHITECTURE.md`, найти нужный файл, внести изменение через `workspace.write` или `workspace.patch`, выполнить `project.test`, показать diff и остановиться после проверки. Автоматическое применение миграций, изменение compose-портов, установка пакетов и доступ к host filesystem остаются подтверждаемыми действиями.

## Roadmap после MVP

Следующие этапы — PostgreSQL/Redis для нескольких пользователей и длительных очередей, настоящая durable event log, worker-процесс, git snapshots/rollback, параллельный Wide Research с лимитами, browser takeover через расширение, визуальный diff, LSP-диагностика и экспорт артефактов. Интеграции с внешними SaaS намеренно не входят в текущий объём.

## Обоснование функций

Публичные материалы Manus описывают изолированный sandbox с файловой системой, сетью, браузером и инструментами [1], явное подтверждение терминальных команд в My Computer [2], browser-операции в текущем разрешённом контексте [3], параллельную декомпозицию Wide Research [4] и переиспользуемые Agent Skills [5]. Uranus-AI переводит эти идеи в локальную Docker-архитектуру с явными границами разрешений.
